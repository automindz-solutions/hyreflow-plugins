### 🟠 AI Ark `find_emails` — `webhook` is REQUIRED
- `POST /v1/people/email-finder` without `webhook` → **400 "webhook is required"**. Results are **pushed** to your webhook URL; there is **no local poll-and-fetch**. The `trackId` then 404s ("expired/not found") because the job never started.
- **Impact:** can't retrieve AI Ark emails locally without a hosted webhook receiver. (Moot for candidate flows — AI Ark is work-email only anyway.)
- **Status:** ✅ FIXED — `lib/aiark.py` docstring + `provider-playbooks/aiark.md` now flag webhook-required + push-only.

### 🟢 O*NET title→code resolution (no code, grep-grounded) — 2026-06-02
- `discover_job_openings` needs `onet_codes`, customers speak in job titles. Decision (COO-approved): **don't build a fuzzy matcher and don't let Claude recall codes from memory** (hallucinated code → wrong results + wasted credits). Instead bundle O*NET 30.3 public-domain tables and let Claude map via GREP.
- Built two **grep-only** reference files: `references/onet-title-index.md` (~58k `Job Title | CODE` short lines, official + reported titles) and `references/onet-occupations.md` (1,016 `CODE | Title | desc` for disambiguation).
- **Why two files / short lines:** first attempt put all synonyms on one line per occupation → the load-bearing occupations (developer/sales/manager) became 1,500-char lines that the **Grep tool OMITS** ("Omitted long matching line"), hiding the code. Flat one-title-per-line keeps the CODE visible on every match. Lesson for any grep-target reference: **keep lines short.**
- Grep cost is line-matched, not file-sized — alt titles don't eat the customer's context (only matched lines load), and they're what makes informal titles ("AE","SDR") resolve. Rule baked into `provider-playbooks/predictleads.md`: grep title-index → root-word fallback → disambiguate via occupations file → confirm if ambiguous → emit only codes present in the files.

### 🔴 `.env` inline comments broke auth — and the fix (new `cli.py`)
- Live crash: `UnicodeEncodeError: 'latin-1' codec can't encode '—'` **inside an HTTP header**. Root cause: the `.env` had trailing inline annotations on the secret lines (e.g. `KEY=<secret>  # X-Api-Key header — …`), and a naive `split('=',1)` swept the em-dash + comment text into the header value. API keys never contain `#`/em-dash → any such char in a key value = a polluted `.env` line.
- **Fix:** a proper loader that strips surrounding quotes AND inline ` #…`/`\t#…` comments. Lives in the new permanent tool below — not hand-rolled per script anymore.

### 🟢 `cli.py` — permanent adapter-invocation tool (replaces temp scripts)
- `python cli.py <tool> <method> [positional...] [--kwarg value]` — loads `.env` (robust loader above), auto-discovers the adapter class in `lib/<tool>.py`, JSON-coerces args (`--limit 1`→int, `--codes '["a"]'`→list), prints JSON, `iter_*`→list. Set `PYTHONIOENCODING=utf-8` to avoid cp1252 console crashes on unicode output.
- **This is the same shape `code.hyreflow.ai` uses** (load creds → instantiate adapter → call method) — so testing via `cli.py` exercises the real production path, not a throwaway. Examples: `python cli.py predictleads financing_events anthropic.com`, `python cli.py github get_rate_limit`.
