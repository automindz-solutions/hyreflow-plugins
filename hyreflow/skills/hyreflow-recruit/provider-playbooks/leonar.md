# Leonar — Integration Meta Skill

HOW in `lib/leonar.py`. Docs: leonar.mintlify.app (published OpenAPI spec).

Leonar is a recruiting sequencer: its **sequences** are the outreach campaigns (email and WhatsApp steps). It also stores the contacts, companies and project pipelines those sequences run on, so one connection covers both the outreach and the records.

## Auth & config (API key)
- **Connect (BYOK):** dashboard **Integrations → Leonar** — paste the **API key**, then **Save and test**. CLI: `hyreflow byok set leonar --api-key <key>`.
- **Get the key in Leonar:** in the Leonar **V2** app, open **Settings → API** and create a key. It starts with `leo_`. Keys from the old V1 app start with `pk_live_` and do not work: Hyreflow refuses them before calling Leonar. API access needs an active Leonar subscription (`billing_required` otherwise), and a feature outside the plan answers `plan_upgrade_required`.
- A key belongs to the Leonar user who created it: messages and enrollments go out from that user's connected email/WhatsApp accounts, and a key only reaches what its scopes allow (a read-only key can't write). The owner's key is the workspace key. By default each member connects their own key (personal keys are on), so what they send goes out from their own accounts and their notes and tasks carry their name; until a member adds theirs, Leonar won't run for them. If the workspace owner turns personal keys off (Integrations, then **Workspace key**), every member runs on the workspace key. Revoking the key in Leonar breaks the connection until a new one is pasted.
- Leonar allows **2000 requests per hour per user**, shared by every key that user owns. Hyreflow paces each key at **30 requests/minute**, which keeps one key under it; two keys of the same user used at the same time can still hit a 429, which is retried.

## Noun mapping
**Sequence** = an outreach campaign: an ordered list of **steps** (email, WhatsApp, call, manual and enrichment steps, with delays and branches); an **enrollment** is one contact in it. **Contact** = any person (candidate or client contact). **Company** = account. **Project** = a recruiting role with its own pipeline of **stages**, and optionally one default sequence. **Pipeline entry** = one contact at one stage of one project. **Conversation** = the message thread with one contact.

## Operations
Sequences (campaigns): read `list_sequences` / `get_sequence` / `list_sequence_steps` / `list_enrollments`, `get_project_sequence`; build and edit (sends nothing while the sequence is draft or paused) `create_sequence`, `update_sequence`, `replace_sequence_steps`, `link_project_sequence` / `set_project_sequence` / `unlink_project_sequence`, `update_enrollment_variables`, `pause_sequence`.
Outreach (reaches real people — gate each one): `activate_sequence`, `resume_sequence`, `enroll_contacts`, `send_message`. Each one is refused unless the payload carries `"confirm": true`, and none of them runs through `batch`: send `confirm` only after the user said yes to that exact call, never to get past the refusal. `unenroll_contacts` stops a contact's remaining sends.
Replies: `list_conversations` / `list_messages`.
Records: read `list_contacts` / `search_contacts` / `get_contact`, `list_contact_notes`, `list_companies` / `get_company`, `list_projects` / `get_project` / `list_pipeline_entries` / `get_pipeline_entry`, `list_tasks`, `list_tags`, `get_enrichment_status`; write `create_contact`, `update_contact`, `add_contact_note`, `add_contact_tag` / `remove_contact_tag`, `create_company`, `add_to_pipeline`, `update_pipeline_entry`, `create_task`, `enrich_contact`.
Bulk: `create_contacts_batch`, `add_to_pipeline_batch`, plus the generic `batch` for get/search/update/create calls (see `crm-bulk-pushes.md`). `batch` refuses the four sending methods, `replace_sequence_steps` and `enrich_contact`.

## Sequences: states and what sends
- **A sequence is `draft`, `active`, `paused` or archived.** Read its state from `status` on `get_sequence` (or `list_sequences`) before any write below; don't assume it from what you just did.
- **Draft and paused are the non-sending states.** `create_sequence` always creates a **draft** (no other status is accepted), and a draft sends nothing until `activate_sequence`. `pause_sequence` stops an active sequence and its pending tasks until `resume_sequence`. Leonar only lets you edit a sequence in these two states: `update_sequence` and `replace_sequence_steps` answer 409 on an active or archived sequence, so pause it first.
- **Building steps on a draft or paused sequence** is not itself the gated act once the user has confirmed the cadence: confirm the state with `get_sequence`, then write the steps. **`activate_sequence` and `resume_sequence` are the gate**: they start or continue live email/WhatsApp sends from the user's connected accounts to every contact enrolled. Show the sequence, its steps and how many contacts are enrolled, and get a yes before either one. Neither is retried on a server error: re-read the sequence's `status` before trying again.
- **`create_sequence`** needs `name` (max 200): `{"name": "Staff Frontend — Paris", "project_id": "<project id>", "steps": [{"client_key": "s1", "type": "email", "subject": "Staff Frontend role at Doctolib", "body": "...", "delay_days": 0}, {"client_key": "s2", "type": "whatsapp", "body": "...", "delay_days": 3}]}`. At most 50 steps here. `project_id` links it as that project's sequence (409 if the project already has one). Other fields: `priority` (normal, high), `mode` (simple, advanced), `owner_ids` (1 to 50), `schedule_config`.
- **`replace_sequence_steps(sequence_id, steps)` replaces the whole list** (at most 100 steps): a step with an `id` is updated, one without is created, and **every existing step you leave out is deleted**. Read the current steps with `list_sequence_steps`, change them, and send the full list back. Leonar refuses it (409) if a step you remove still has pending tasks. On a paused sequence, the new steps are what enrolled contacts get when it resumes.
- **`update_sequence`** changes only `name`, `priority`, `mode`, `owner_ids` and `schedule_config`. The state changes only through `activate_sequence`, `pause_sequence` and `resume_sequence`.
- **A project's default sequence:** `get_project_sequence` reads it. `link_project_sequence(project_id, sequence_id)` links an existing one, or `link_project_sequence(project_id, sequence={...})` creates a new draft (same fields as `create_sequence`) and links it; both answer 409 if the project already has one. `set_project_sequence` replaces the link, and `unlink_project_sequence` only detaches it: the sequence is kept.
- **Per-contact variables after enrolling:** `update_enrollment_variables(sequence_id, contact_id, {"custom_variable_2": "..."})` changes one enrolled contact's values (keys you leave out are kept, `null` clears one). It never sends anything itself; steps not yet processing use the new values, and a step already processing or a manual task already created keeps the old ones.
- **`enroll_contacts` starts real outreach** as soon as the sequence is active. Pass either `contact_ids` or `contacts` (`[{"contact_id": ..., "custom_variables": {...}}]`), not both, at most 500 per call either way (`unenroll_contacts` too). Leonar skips contacts marked do-not-contact, already in this sequence or active in another one, and returns the counts (`enrolled`, `skipped_blacklisted`, `skipped_already_enrolled`, `skipped_active_elsewhere`, `skipped_not_found`): report them. Enrolling always stays gated, whatever state the sequence is in: confirm the sequence and the list with the user first.

## Notes & guardrails
- **Paging:** every `list_*` takes `limit` (1 to 100, default 50) and `offset` (from 0). A larger `limit` is rejected, not trimmed. Keep raising `offset` by `limit` while the response's `meta.has_more` is true; `meta.total` is the full count. `search_contacts` takes `limit` and `offset` in its request body: `limit` must be at least 1, and Leonar documents no maximum for it, so page with `meta.has_more` rather than assuming a page size.
- **Find before you create:** `search_contacts` takes `query` (full text) or `name`, `title`, `company`, `location`, `tags`, `project_id`, `sequence_id`. Search first and update the match with `update_contact` instead of creating a second record.
- **`create_contact`** needs `first_name`: `{"first_name": "Sophie", "last_name": "Martin", "title": "Senior Software Engineer", "current_company": "Doctolib", "emails": [{"email": "sophie@doctolib.com", "type": "work"}], "linkedin_profile": "https://www.linkedin.com/in/sophie-martin", "tags": ["frontend"]}`. Up to 5 `emails` and 5 `phones`. `tags` are names and are created if they don't exist. `custom_data` is keyed by the workspace's custom field keys.
- **`update_contact`** changes only the fields you send. In `custom_data`, a key set to `null` is removed and keys you leave out are kept.
- **Tags on an existing contact** go by id: read them with `list_tags`, then `add_contact_tag(contact_id, tag_id)`. `remove_contact_tag` only detaches the tag.
- **Pipeline stages are ids, not names.** Read a project's stages with `get_project` (`data.pipeline.stages`), then pass the stage's id as `stage_id`. `add_to_pipeline(project_id, contact_id)` without a `stage_id` lands the contact in the first stage. Move a contact with `update_pipeline_entry(entry_id, {"stage_id": "<stage id>"})`; only the fields you send change.
- **Custom variables** (on `add_to_pipeline`, `update_pipeline_entry`, `enroll_contacts` and `update_enrollment_variables`) are the fixed keys `custom_variable_1` to `custom_variable_5`, each at most 2000 characters. Any other key is rejected. They fill the `{{custom_variable_N}}` placeholders in the sequence's messages.
- **Enrichment** spends the customer's Leonar enrichment credits: `enrich_contact(contact_id, type)` with `type` = `work_email`, `personal_email` or `phone` returns a `request_id`; poll `get_enrichment_status(request_id)` until `status` is `completed` or `failed`. Confirm before enriching a list, one contact per call: `batch` refuses `enrich_contact`.
- **`send_message` sends immediately** to a real person from the user's connected account: `channel` is `email` (needs `subject`) or `whatsapp`. Show the exact message and get a yes before every send. It is not retried on a server error, because the message may already have gone out: check `list_conversations` for the contact before sending again.
- **No record delete** is exposed. The one write that removes anything is `replace_sequence_steps`, which deletes the steps you leave out; the generic `batch` refuses it.
- Production writes: pilot one record, confirm, then bulk.

## Handoff
Outreach: enriched candidates → `create_contact` (or `create_contacts_batch`) → `add_to_pipeline` on the role's project (or `add_to_pipeline_batch`) → the project's sequence (`get_project_sequence`, or `create_sequence` as a draft with its steps) → after the user approves, `enroll_contacts` and, for a draft, `activate_sequence`. Replies come back as `list_conversations` / `list_messages` and as enrollment `status` (`replied`, `bounced`) on `list_enrollments`; log call notes with `add_contact_note` and follow-ups with `create_task`.

## Bulk writes & rate limits

For large pushes use `create_contacts_batch` and `add_to_pipeline_batch` (each payload `{contact_id, stage_id?, custom_variables?}`, plus `project_id` once for the whole list). They pace calls to the **30 req/min** default and return `{created, failed, total, elapsed_ms}`. At that pace 500 contacts take about 17 minutes. See `crm-bulk-pushes.md` for the cross-CRM guide.
